## 0. TL;DR

The project is **three strong, mostly-disconnected pillars** plus a thin FE. Each pillar is individually credible; the **end-to-end demo flow is not wired**, and the single most-load-bearing piece of plumbing (Aiven Kafka) **isn't provisioned**. The biggest risk is not "nothing is built" — it's "two of the best-built parts contradict the binding architecture and don't talk to each other."

- ✅ **KG data layer is real and fast.** A live Aiven Postgres+pgvector graph seeded with 6,183 nodes / 26,179 edges from `anthropic-sdk-python`; hybrid OpenSearch→PG retrieval measured at ~125 ms trans-Atlantic.
- ✅ **Agent-runner container is real.** Warm Aiven-MCP session, Kafka consumer, shared harness lifecycle, working **git-agent** that answers from the graph via `aiven_pg_read`. This is the MCP-native showpiece and it largely works.
- ✅ **Listener ("avatar-agent") is real and ambitious.** LiveKit + Recall + Anam photorealistic avatar, real-time STT→LLM→TTS, terraform deploy. The "face on the call" wow factor exists.
- 🔴 **They don't connect.** The avatar-agent reaches data over **HTTP to `central-kg-api`** (the exact anti-pattern the plan forbids) and emits **no Kafka tasks at all**. The agent-runner consumes `agent.tasks.*` that **nothing produces** except a dev script. The demo's headline sentence ("delegate work mid-call") has no live path.
- 🔴 **Aiven Kafka is not provisioned** (no free tier). The entire dispatch spine currently only exists as local redpanda.
- 🟡 **The best-built code is unmerged.** The seed loader, demo transcripts, bench, and tests live on `feat/demo-data-layers`; the entire Listener lives on `ferg/avatar-agent`. `main` doesn't contain either.

## 2. What's built, pillar by pillar

### 2.1 Knowledge Graph (`central-kg-api` + seed) — **strongest pillar**
- **FastAPI service** on `main`: routers for `ingest, extract, link, query, entity, subgraph, timeline, update`; `graph.py`, `embeddings.py`, `db.py`, Mangum/Lambda entrypoint. The "FE/seed bridge" role from the plan is real code.
- **Seed pipeline** (on `feat/demo-data-layers`): graphify → `graph.json` → bulk upsert; git-history seeding (commits/people/AUTHORED/TOUCHES); demo-meeting seeding with grounded mentions; OpenSearch mirror.
- **Live, measured:** 6,183 nodes + 26,179 edges seeded; hybrid retrieval ~124–134 ms warm trans-Atlantic; OpenSearch BM25 3–57 ms, PG recursive CTE 1–6 ms. **This is demo-bankable data that already exists in Aiven `jq01`.**
- **Tests exist** for the resolver + graphify adapter.

### 2.2 Agent-runner container (`agent-system/`) — **strong, MCP-native**
- **Real:** `shared/mcp.py` (warm local `mcp-aiven` stdio, programmatic + LLM-exposed paths), `shared/harness.py` (full validate→dedupe→act→emit lifecycle, direct-Kafka emits), `shared/kafka.py`, `shared/contracts.py` (clean pydantic envelope + payloads), `shared/sessions.py`, `runner.py` (long-lived consumer, bounded `asyncio` concurrency, graceful no-creds degradation).
- **git-agent: working** — streams a `tool_runner` turn that issues `aiven_pg_read` against the seeded graph and answers in 1–2 sentences. This is the literal 34%-criterion showcase.
- **echo agent: working** — proves the consume→harness→emit loop with no creds.
- **web-agent / data-agent: stubs** — return `{"status": "stub"}`. The plan calls web-agent "the best demo"; it does not exist yet.
- **Local-first dev** works: redpanda compose, `scripts/publish_task.py` stands in for the listener, `Makefile`, `.env.example`.

### 2.3 Listener / avatar-agent (`ferg/avatar-agent`) — **strong but off-architecture**
- **Real:** LiveKit Agents pipeline (STT→LLM→TTS), Recall transport, Anam avatar render, 4 tools (`lookup_context`, `get_entity`, `recent_activity`, `record_action_item`), observability, full terraform (LiveKit on EC2 + Lambda dispatch + ECR + network), a browser viewer, tests.
- **Data path:** `httpx` calls to `central-kg-api` (`GET /query`, `/entity`, `/timeline`, append events).
- **No Kafka. No `agent.tasks.*`. No `shared/contracts`.**

### 2.4 Frontend (`meet-joiner/`) — **thin**
- Minimal Next.js app with a themed UI and a `POST /api/join` route that validates a Meet URL and dispatches a bot. It is a **bot-launcher**, not the "live transcript + agent activity feed + ask box" overlay the plan describes. No WS bridge to agent activity.

## 3. Contradictions & tensions (what fights what)

1. **🔴 The Listener violates the binding MCP-native mandate.** PLAN §3.5 and AGENT_SYSTEM §7 are explicit and "binding": *agents talk to data via Aiven MCP; the FastAPI is for the FE only; agents must not call the HTTP API at all.* The actually-built Listener (`avatar-agent`) does the forbidden thing — it reaches the graph over **HTTP to central-kg-api**. For the 34%/33% rubric this is the exact penalized pattern ("backend boilerplate between an agent and a DB"). Either (a) re-point its tools at `mcp-aiven` like the git-agent already does, or (b) consciously accept central-kg-api as the Listener's read path and **drop the "no HTTP" absolutism from the docs** so the story is coherent. Right now code and doctrine disagree.

2. **🔴 No producer for `agent.tasks.*`.** The whole "delegate work mid-call" thesis needs the Listener to emit `task.create` onto Kafka. The Listener emits nothing to Kafka. The agent-runner consumes a topic only `scripts/publish_task.py` writes to. **The end-to-end demo flow is two halves with no bridge.**

3. **🔴 Aiven Kafka isn't provisioned** (infra README: "Not provisioned yet; needs a paid plan"). The dispatch spine — the thing the Aiven challenge most rewards (Kafka pub/sub via MCP) — exists only as local redpanda. This must be resolved to show Kafka-on-Aiven at all.

4. **🟡 Two/three deployment topologies, none integrated.** agent-runner → ECS/EC2 container; avatar-agent → LiveKit-on-EC2 + Lambda dispatch + terraform; central-kg-api → Lambda/Mangum. Three deploy stories, zero shared infra wiring. Fine for a hackathon if the demo runs locally, but it means "deploy" is not one button.

5. **🟡 "avatar-agent" vs the plan's "Listener."** AGENT_SYSTEM explicitly removes the call/listener from "our folder" and calls it a teammate's separate container — and indeed it is a separate branch. But it was built as a *self-contained product* (its own avatar, its own backend client, its own deploy), not as a component that emits onto the shared bus. The seam the docs promised ("produces `agent.tasks.*`") was never implemented.

6. **🟡 Doc surface is heavier than the integration surface.** ~2,000 lines of excellent planning docs (PLAN, AGENT_SYSTEM, HACKINFO, CENTRAL-KG-API) describe a system more wired-together than the code is. The docs are an asset for the *written* Anthropic submission; just don't mistake them for the system state.

7. **🟢 Minor:** git-agent hardcodes `project "jq01" / service "central-kg-pg"` in its system prompt — acceptable coupling for the hack, worth a config var later.

## 4. Opportunities

- **One bridge unlocks the headline demo.** Add a Kafka producer to the Listener's `record_action_item`/delegation tool so an actionable utterance emits `task.create` → git-agent answers from the graph → result streams back. That single wire turns three pillars into one system. It is the highest-leverage change available.
- **The KG data already exists and is fast.** You can demo "who last touched the auth module" against real, seeded data *today* — no live seeding needed on stage. Lean on this; it's your most reliable moment.
- **git-agent is already the 34% proof.** Record it issuing `aiven_pg_read` through `mcp-aiven` on camera. It needs no new code to be a rubric centerpiece.
- **Provision Kafka via MCP on camera = the 33% autonomy proof.** Turning the un-provisioned Kafka into an `aiven_service_create` + `aiven_kafka_topic_create` MCP moment converts the current gap into the exact "autonomy" evidence judges want.
- **web-agent is the creativity multiplier.** Even a tiny static-site → Vercel deploy from a mid-call brief is the visual "wow." It's stubbed; a minimal real version is high ROI for the 33% creativity score.
- **The avatar is a differentiator most teams won't have.** A photorealistic talking face on the call is memorable in a 4-min pitch regardless of backend purity.

## 5. Next steps by trajectory

### Trajectory A — "Win the demo" (recommended for the 4-min pitch)
Goal: one continuous on-stage flow. Priority order:
1. **Merge `feat/demo-data-layers` → `main`** so the seed + tests + transcripts are on the integration line.

5. **Ship a minimal real web-agent** (static site → Vercel) for the visual payoff.
6. Rehearse the exact sentence: *"build us a landing page and tell me who last touched the auth module."*

### Trajectory B — "Win the written Anthropic submission"
The docs are already strong. Focus on: an honest architecture diagram that matches the *code* (not the aspiration), a crisp MCP-depth narrative (git-agent + Kafka-provision-on-MCP), and screenshots/logs of real `aiven_pg_read` calls. The written submission can legitimately describe the full design as long as the demo proves the core MCP loop.

### Trajectory C — "Architectural coherence" (if there's slack)
Collapse the contradiction permanently: make **every** data touch (Listener included) go through `mcp-aiven`, demote `central-kg-api` to seed+FE only as the plan intends, and unify deploy into one story. This is the "right" system but the most expensive; only pursue after Trajectory A's demo is locked.

## 6. How I see the project progressing

The team did the hard, correct thing first: **deep research + a binding plan + a real data layer**. The KG and the MCP-native git-agent are genuinely differentiated against a typical hackathon field, and the avatar is a memorability asset. The project's whole remaining risk is **integration, not capability** — the parts are built; the wires between them aren't, and one of the parts wandered off the architecture.

The fastest path to a winning state is not more building — it's **three wires and a merge**: (1) merge the data branch, (2) provision Kafka on camera, (3) emit one task-create from the Listener, (4) reconcile the Listener's data path with the MCP mandate. Each is hours, not days. Do those and the project goes from "three impressive demos" to "one system that does the thing the pitch promises" — which is exactly what the rubric (MCP depth + autonomy + impact) rewards.

The thing to guard against: polishing pillars in isolation (more avatar realism, more KG routes) instead of closing the seams. The marginal pillar is already good enough; the marginal *wire* is worth far more right now.
