## 0. TL;DR

The **forward** pipe is now well-built: `transcript → planner → tasks → agents → results → FE`, with reasoning streaming (`agent.trace`) on top. The weakness is everything **downstream of "answer"**: the system has **no memory of its own data**. Three structural facts:

1. **The KG is read-only at runtime.** The graph is seeded once (tree-sitter + git) and never learns again — not from meetings, not from agent results. `kg.updates` is a topic with **zero producers and zero consumers**; `central-kg-api` has **no Kafka code at all**.
2. **Retrieval is trigram-only.** Both fancier paths are scaffolding: **embeddings are stubbed** (`embed_*` return `None` → pgvector branch never taken) and **OpenSearch BM25 (`/search`) is built but uncalled** (the avatar hits `/query`, which falls to `ILIKE`).
3. **The meeting — the richest live context — evaporates.** Transcript is routed and displayed, then dropped; the post-call artifact is written to disk and read by nothing; the one meeting→KG write (`record_action_item`) is **contract-broken** (loses the text).

None of these block the demo. All of them are the difference between "a pipeline that runs" and "a knowledge graph that compounds." Highest-leverage fixes are small (§7).

## 2. Transcript processing — how it's handled, and how it could be better

**Today:** each *final* user utterance → gateway → `meeting.transcript` → (a) the planner LLM-routes it to tasks, (b) the FE feed shows it. Then it's gone.

Three concrete weaknesses:

- **The planner is stateless.** It routes each utterance in isolation (`messages=[{"role":"user","content": text}]`) and its prompt literally tells the model *"the agent does not see the conversation."* Multi-turn requests ("build that page… make it dark… add the pricing we discussed") can't resolve — each line is judged alone. *Fix:* feed a short rolling window (last N finals) or a running summary into `plan_utterance`; dedupe on a content hash, not just envelope id, so a re-statement isn't re-delegated.
- **Transcript never enriches the KG.** The meeting is the one *live* data source, and it's the only one the graph the avatar reads from never sees. *Fix:* tee settled utterances to `central-kg-api` `/extract` (which already turns free text → nodes/edges) or emit `kg.updates`. Then "who owns billing" can be answered from *what was just said*, not only the seeded code graph.
- **The post-call artifact is the obvious feedstock and it's orphaned.** `CallArtifact` writes `{transcript, tool_calls}` JSON to disk; nothing reads it. *Fix:* on shutdown, POST the transcript to `/ingest` (one call) — instant per-meeting KG enrichment with zero hot-path cost.

## 3. The missing feedback loop (the single biggest opportunity)

`kg.updates` exists in `config.ALL_TOPICS`, has a `KgUpdatePayload` contract that says *"consumed by central-kg-api,"* and is **wired to nothing** — no producer, no consumer, and `central-kg-api` imports no Kafka client. So:

- Built sites, git/KG answers, data findings — **none are persisted.** Every question is recomputed from scratch; the suite has no memory of its own work.
- The designed write-back path is a labelled pipe with no ends.

*Fix (small, high-leverage):* add **one consumer** — either inside `central-kg-api` (apply `KgUpdatePayload` via the existing `upsert_node`/`upsert_edge`) or a tiny sidecar tailing `agent.results` that upserts a `built_site`/`answer` node. This turns the swarm from stateless Q&A into an **accumulating graph** — and it's *more* live MCP write surface, which is the 34% rubric axis.

## 4. Retrieval reality — trigram, despite hybrid scaffolding

The avatar's `lookup_context` → `/query` → `hybrid_search`, which **awaits `embed_one` (always `None`) then falls to trigram/`ILIKE`** every call. Two fully-built better paths sit unused:

- **OpenSearch BM25** (`/search`, recursive-CTE neighborhood) is registered and indexed at seed — but nothing calls it. **One-line win:** point the avatar's `backend.query()` at `/search` instead of `/query` → real relevance ranking immediately.
- **pgvector** schema, `<=>` SQL, and 0.7/0.3 blend weights all exist — dead because `embeddings.py` is a stub. **Implement one adapter** (Voyage/ST) + run `bulk_embed_nodes` → the whole semantic path activates with no caller change.

Net: live retrieval is name-similarity only; the seed/mirror cost currently buys nothing at query time.

## 5. Confirmed bug — `record_action_item` loses the text

The avatar's one meeting→KG write is contract-mismatched.

- Avatar POSTs `{"node":"meeting","kind":"action_item","body": "<text>"}` (`avatar-agent/.../backend.py:append_event`).
- `/update`'s `EventCreate` (`central-kg-api/app/models.py:111`) is `{node_id: UUID|None, source_id, kind, payload}`.
- Result: `node` + `body` are **silently dropped** (pydantic ignores extras), `node_id` is NULL, `payload` is `{}`. The events row persists with **no action-item text and no node link** — yet the tool says *"Done — I've recorded the action item."*

*Fix:* send `{"kind":"action_item","payload":{"description":..., "owner":...}}` (and optionally upsert a `meeting`/person node first to set `node_id`). Classify: **bug** — silent data loss on the one write the avatar makes during a call.

## 6. Efficiency & correctness flaws (lower priority)

- **Idempotency is in-memory per process** (`harness.py` `ctx._seen` is a plain set). Kafka at-least-once + multiple runners/restarts → duplicate task execution, incl. the web-agent's expensive build and any `aiven_pg_write`. *Fix later:* a durable/shared dedupe (Redis or a KG `task_id` check).
- **git-agent runs a full LLM tool-loop per question** — ≥2 model turns to write+read SQL — with no templating/caching, even for repeat or templatable intents (`who touched X`). Its own docstring flags templated SQL as the planned optimization.
- **Wasted `embed_one` await on every `/query` and `/subgraph?q=`** — a pointless async call that always returns None before the fallback.
- **Two delegation brains can still double-fire across the seam:** the planner and (if `AVATAR_DELEGATES=true`) the avatar both mint random task ids, so per-task-id dedupe won't catch the same utterance delegated twice. Default config avoids it (planner-only); just don't enable both.
- **web-agent artifacts are ephemeral & unauth'd** (local disk, `SimpleHTTPRequestHandler`, `0.0.0.0`) — the demo's main deliverable dies with the process. *For a judge-clickable URL,* persist to object storage or push to Vercel.
- **OpenSearch calls use `verify=False`** — fine for the hack, a TLS flaw for prod.

## 7. The Aiven Kafka switch — exactly what's needed

The cluster (`kafka-254bd14f`) is provisioned; the code fully supports Aiven **mTLS** today — **no code edits required.** Host-mode checklist:

1. **Fetch creds** (needs `AIVEN_TOKEN` + `avn` CLI): `uv run python scripts/fetch_kafka_creds.py` — writes `ca.pem` / `service.cert` / `service.key` into `agent-system/` (all gitignored) and **prints the exact `.env` block**, including the real `KAFKA_BOOTSTRAP` and computed `KAFKA_RF`.
2. **Paste that block** into `agent-system/.env`:
   ```
   KAFKA_BOOTSTRAP=<service_uri>      KAFKA_SECURITY=SSL
   KAFKA_CA_PATH=./ca.pem   KAFKA_CERT_PATH=./service.cert   KAFKA_KEY_PATH=./service.key
   KAFKA_PARTITIONS=3   KAFKA_RF=<printed value>
   ```
   (mTLS needs no `KAFKA_USERNAME`/`PASSWORD`.) Ensure no other `.env` reasserts `PLAINTEXT` — `load()` merges nearest-wins.
3. **Confirm topics:** `uv run python scripts/provision_topics.py --service kafka-254bd14f --create` (idempotent). ⚠️ **Topic-count check:** code now lists **10** topics (`ALL_TOPICS` includes the new `agent.trace` + `kg.updates`); only **9** were reported provisioned — create the missing one before relying on it.
4. **Verify:** `make smoke` (`scripts/kafka_smoke.py`) — produces + reads back on `agent.results`; honors the SSL env despite its "no creds" docstring.
5. **Run host-mode:** `make run` / `make planner` / `make gateway` read the env directly.

**Gotchas:** (a) `docker compose` **hardcodes** `KAFKA_BOOTSTRAP: redpanda:9092` + `PLAINTEXT` in the `environment:` block, which overrides `env_file` — `make stack` is local-only as written; host-mode is the clean path to Aiven. (b) CA path is `./`-relative → run from `agent-system/`. (c) The expired-`AIVEN_TOKEN` finding from `03-23Z` blocks *both* this fetch and the MCP read path — re-auth first.
